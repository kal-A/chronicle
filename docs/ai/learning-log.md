## 2026-08-05 — Phase E1: Model Provider Foundation

**No agent exists yet this entry is early** — these are provider-layer, not agent-layer, lessons. Agent-specific entries (tool-selection accuracy, critic correction rate, etc.) start at E3/E4.

- **Hardware reality changed the model decision materially.** The initial instinct going into E1 was to pick a model on capability alone; the actual hardware audit (13.69 GB total RAM, integrated GPU with no realistic Ollama acceleration on Windows) cut the practical ceiling to roughly 7-8B parameters at Q4 quantization before any capability comparison mattered. Lesson for future provider/model decisions on this project: audit hardware *before* comparing models, not after — it changes which comparison is even worth making.
- **Retry-policy design needs an explicit, stated rule for which failures are worth retrying, or it becomes inconsistent under real testing.** While writing `OllamaModelProvider`'s retry logic, a genuine design bug surfaced during testing: HTTP 5xx responses were initially bucketed under the same `ProviderUnavailableError` as a flat connection refusal, but one test implicitly expected 5xx to be retried while another (correctly) expected connection-refused not to be. Resolved by treating both as non-retryable — a local Ollama daemon returning 500 usually indicates a real problem (crashed model process, OOM, malformed request), not a transient blip a same-millisecond retry would fix — but the fact that the inconsistency wasn't obvious until a test caught it is the actual lesson: retry-eligibility needs to be a named, reasoned-about set (`orchestration/policies.py`'s `RETRYABLE_ERROR_TYPES`) checked in tests for *every* error type individually, not inferred ad hoc per call site.
- **Structured-output retry-with-feedback is untested against a real model as of this entry.** `OllamaModelProvider`'s retry-with-validation-feedback behavior is verified against `httpx.MockTransport` (deterministic, scripted responses), which proves the *mechanism* works but says nothing about whether real Qwen2.5:7b-instruct output actually improves when shown its own validation error. That's the first thing to check once Ollama is actually installed and E3's Planner exists to generate a real structured-output failure to observe.
- **One model reused across four roles is an assumption, not yet a measured result.** `docs/ai/model-provider-decisions.md` states the rationale (hardware can't hold more, and it isolates the multi-agent-design question from the bigger-model question) but this is a prediction to be checked by E7's evaluation, not a settled fact — record here whether it holds once real agent evaluation exists.
