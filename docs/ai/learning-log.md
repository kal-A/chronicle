## 2026-08-05 — Phase E1: Model Provider Foundation

**No agent exists yet this entry is early** — these are provider-layer, not agent-layer, lessons. Agent-specific entries (tool-selection accuracy, critic correction rate, etc.) start at E3/E4.

- **Hardware reality changed the model decision materially.** The initial instinct going into E1 was to pick a model on capability alone; the actual hardware audit (13.69 GB total RAM, integrated GPU with no realistic Ollama acceleration on Windows) cut the practical ceiling to roughly 7-8B parameters at Q4 quantization before any capability comparison mattered. Lesson for future provider/model decisions on this project: audit hardware *before* comparing models, not after — it changes which comparison is even worth making.
- **Retry-policy design needs an explicit, stated rule for which failures are worth retrying, or it becomes inconsistent under real testing.** While writing `OllamaModelProvider`'s retry logic, a genuine design bug surfaced during testing: HTTP 5xx responses were initially bucketed under the same `ProviderUnavailableError` as a flat connection refusal, but one test implicitly expected 5xx to be retried while another (correctly) expected connection-refused not to be. Resolved by treating both as non-retryable — a local Ollama daemon returning 500 usually indicates a real problem (crashed model process, OOM, malformed request), not a transient blip a same-millisecond retry would fix — but the fact that the inconsistency wasn't obvious until a test caught it is the actual lesson: retry-eligibility needs to be a named, reasoned-about set (`orchestration/policies.py`'s `RETRYABLE_ERROR_TYPES`) checked in tests for *every* error type individually, not inferred ad hoc per call site.
- **Structured-output retry-with-feedback is untested against a real model as of this entry.** `OllamaModelProvider`'s retry-with-validation-feedback behavior is verified against `httpx.MockTransport` (deterministic, scripted responses), which proves the *mechanism* works but says nothing about whether real Qwen2.5:7b-instruct output actually improves when shown its own validation error. That's the first thing to check once Ollama is actually installed and E3's Planner exists to generate a real structured-output failure to observe.
- **One model reused across four roles is an assumption, not yet a measured result.** `docs/ai/model-provider-decisions.md` states the rationale (hardware can't hold more, and it isolates the multi-agent-design question from the bigger-model question) but this is a prediction to be checked by E7's evaluation, not a settled fact — record here whether it holds once real agent evaluation exists.

## 2026-08-05 — Phase E1 closeout: first real Ollama structured-output call

The first real model call this project has ever made. Full report: `docs/delivery/phase-e1-real-model-smoke-test-report.md`. Test: `backend/tests/ai/integration/test_ollama_smoke.py` (marked `local_ollama_integration`, excluded from the default suite).

- **Ollama 0.32.5**, installed via `winget install Ollama.Ollama --scope user` (official package, matches the upstream GitHub release installer). Model **`qwen2.5:7b-instruct`**, digest `845dbda0ea48ed749caafd9e6037047aa19acfcfd82e704d7ca97d631a0b697e`, 4,683,087,332 bytes on disk (~4.7 GB). `ollama show` confirms **Q4_K_M** quantization, 7.6B parameters — matches `docs/ai/model-provider-decisions.md`'s prior prediction exactly, not assumed this time.
- **First attempt succeeded — no retry needed.** The retry-with-feedback mechanism (previously verified only against `httpx.MockTransport`) was never exercised for real, because the model didn't need it: `qwen2.5:7b-instruct` produced schema-valid JSON on the first try for this trivial three-field schema. This is genuinely informative but narrow — it says nothing about whether retry-with-feedback helps on a harder, more nested schema (`AnalysisDraft`, `CriticDecision`); that remains untested.
- **Latency: ~21.0 seconds** for a ~90-token round trip (70 prompt + 18 completion tokens per Ollama's own usage report) on this hardware (Ryzen 5 6600H, CPU-only, 13.69 GB RAM). Slow relative to a hosted API, as predicted, but not impractical for a single interactive step — this project's own design (bounded, sequential agent calls, no parallelism) is a reasonable fit for that latency, not a mismatch.
- **No sustained memory pressure observed**, though the live sampling attempt itself failed (a `Start-Job` background sampler didn't survive between tool calls in this environment and produced zero samples — a tooling gap, not a system-stability finding). What's actually known: free RAM was ~1.56 GB immediately before the call and ~1.63 GB immediately after (stable, not depleted); the Ollama daemon's working set dropped back to ~29 MB after the call, meaning the model did not stay resident; Windows' `Microsoft-Windows-Resource-Exhaustion-Detector` event log had zero entries across the entire install+pull+test window. This is reasonable evidence against severe pressure, not a peak-memory measurement — a genuine gap, honestly disclosed rather than papered over with an invented number.
- **Ollama reports a 32768-token context length** for this model (`ollama show`'s "context length" field) — this is the model's architectural maximum, not a claim about what's safely usable given this machine's ~13.69 GB RAM. `docs/ai/model-provider-decisions.md`'s prior "~8K practical context window" estimate is this project's own conservative guess for safe usage under this RAM budget; this smoke test's ~90-token exchange is far below either number and confirms neither.
- **Cost recorded correctly**: `amountUsd=0.0`, `basis=NO_PROVIDER_CHARGE`, exactly as designed at E1 closeout — the first real call to actually exercise that field outside a test double.
- **Practical conclusion**: the provider wiring works end to end against a real model, for a trivial schema, once. It says nothing yet about complex nested agent contracts, historical reasoning, tool calling, or sustained/repeated load — all still untested, all E3+ work.
