# ADR-003: The LLM-Agent System Is the Product Core

**Status:** Accepted — 2026-08-05

## Context

Phases A-D built a versioned `GeneratedInvestigation`/`InvestigationExperiencePlan` contract, a deterministic Python generation pipeline (mock and real curated provider sets), and a map-first workspace with a persistent Ask panel — but the Ask panel is a disclosed placeholder (`AskTab.tsx`) and the Ask entry surface (`src/features/investigation/ask/`) only keyword-matches against the two packages that already exist. No live model call has been made anywhere in this codebase. `AGENTS.md` §8 and every phase through D0.6 explicitly deferred live search/model calls "past Phase C" without yet specifying when that deferral ends.

Kamal supplied a six-document instruction set (`docs/ai-core-instructions/00_START_HERE.md` through `06_CLAUDE_CODE_EXECUTION_INSTRUCTIONS.md`, preserved verbatim there) correcting Chronicle's product framing: the domain-specialized LLM/multi-agent system — not the Concert of Europe/Blank Cheque content — is the actual product and portfolio objective. The historical domain is the proving ground the AI system is developed, evaluated, and demonstrated against, not a growing set of hand-curated investigations. This is a genuine, expensive-to-reverse product-framing change, and a full pivot of the roadmap from Phase E onward — the same weight of decision as ADR-002's Phase D insertion, which itself required explicit approval before any code changed.

Two things needed resolving before any implementation could start, since the instruction set's own required audit (`06`, "First response required before editing") surfaced a direct conflict with a standing written constraint:

- `AGENTS.md` §5 ("Cost Constraints") currently reads: *"No paid infrastructure required to develop or demo the project... Ollama + open-weight models... for AI runtime"* and *"Any new paid dependency must be explicitly proposed with a written justification... and requires Kamal's approval before adoption."* The new instruction set requires "one real provider" (document `02` §9, document `05` E1) without specifying which.
- `docs/delivery/revised-development-phases.md` already had a Phase E ("Real Discovery and Assessment") through Phase L fully lettered and described (from ADR-002's own D-insertion cascade). The new instruction set's own Phase E-K sequence (document `01` §5) reuses the same letters for different content.

Both were put to Kamal directly rather than assumed. Answers below.

## Decision

1. **The LLM-agent system is now the product core.** Four bounded agents — Investigation Planner, Evidence Analyst, Historical Critic, Investigation Guide (document `02`) — operate over existing corpora via typed deterministic tools, not an open-ended agent swarm (`AGENTS.md` §4's "no autonomous agent swarms" continues to bind). The map-first workspace, the `GeneratedInvestigation`/`InvestigationExperiencePlan` contracts, the provenance model, and the deterministic providers are **not discarded** — they become the AI system's infrastructure: retrieval corpus, output contract, interaction surface, and audit trail, respectively (document `01` §4's reinterpretation table).
2. **The real model provider is local, open-weight, via Ollama** — not a paid hosted API. This keeps the decision inside `AGENTS.md` §5's existing constraint exactly as written; no cost exception is being requested. The accepted tradeoff: a smaller local model is measurably weaker at reliable structured output and multi-step tool use than a frontier paid API, which places real weight on E1's retry-on-malformed-structured-output requirement and on the E7 evaluation harness actually being able to show the four-agent design earns its complexity (document `04` §9) rather than every baseline being uniformly weak. Ollama is not installed on the current development machine as of this ADR — a manual setup step, not a code blocker for E1 (real-provider integration tests are designed to skip gracefully when Ollama isn't reachable).
3. **The roadmap's Phase E-L section is replaced wholesale** with the new instruction set's Phase E-K sequence: **E** Real LLM Agent Core, **F** Autonomous Source Discovery, **G** Document Acquisition and RAG Corpus, **H** Historical Model Generation, **I** Chronicle Task Model Experiment, **J** AI Geographic and Experience Composer, **K** Full Autonomous Investigation. The former Phase E ("Real Discovery and Assessment") and Phase F ("Acquisition and Corpus Retrieval") content is not lost — it is absorbed into the new Phase F and Phase G respectively, resequenced *behind* the AI core instead of ahead of it. Former Phase G-L do not have a clean one-to-one mapping into the new I-K set (the new sequence reorganizes around AI-system maturity, not source-pipeline maturity); their content is treated as superseded by the new sequence's phase gates rather than individually remapped.
4. **Sequenced as separately-approved sub-plans**, mirroring every prior phase in this project (C0-C3, D0.1-D0.6): E0 (this ADR + doc reorientation + a checkpoint commit of the then-uncommitted C0-D0.6 work), then E1 (model-provider protocol) → E2 (corpus service + tools) → E3 (Planner + Analyst) → E4 (Critic + Guide) → E5 (FastAPI + streaming) → E6 (real Ask-panel integration) → E7 (evaluation harness) → E8 (domain generalization: a second small benchmark corpus, no-topic-branching checks) → E9 (`docs/ai/` learning documentation).
5. **Frontend expansion freezes** until the AI core works (document `01` §6): no new static investigations, no new lenses without an AI consumer, no more hand-authored provider sets, no more deterministic-"generation" UI simulations. Frontend changes are scoped to connecting the live assistant once E6 is reached.
6. **Explicit exclusions carried forward from document `05`**, none of which are in scope until their own later, separately-approved phase: unrestricted live web research, broad scraping, OCR, a production vector database, full autonomous new-topic generation, map-asset discovery, fine-tuning, public publishing, collaboration, user accounts.

## Consequences

- `AGENTS.md` §5's example stack line ("Ollama + open-weight models... for AI runtime") is no longer just an aspirational preference — it is the actual, load-bearing choice for Phase E's real provider. A future decision to add a paid API provider alongside or instead of Ollama is a new, separately-justified cost exception per §5's own rule, not something this ADR pre-approves.
- Every future reference to "Phase E" in this codebase means the AI agent core, not source discovery — source discovery is now Phase F. `docs/delivery/revised-development-phases.md`, and any other doc cross-referencing the old E-L lettering, needed updating as part of this ADR landing (E0's doc-reorientation step).
- `docs/architecture/ai-agent-architecture.md` already described a bounded, tool-using assistant pipeline in outline (`ai-agent-architecture.md`'s existing "User Assistance" subsystem) — this ADR makes that outline concrete (the four named agents, their typed contracts) rather than introducing a conflicting design.
- `docs/architecture/provenance-and-review.md` describes a Postgres/pgvector/human-review "Studio" system (review-status state machine, ImpactReview, Shared Evidence Network) that was never built — only file-based, no-database persistence exists today (`RunStore`, C1). E2's corpus service queries the **already-generated `GeneratedInvestigation` package's own embedded records**, not a database that doesn't exist; this gap is now flagged explicitly in that document rather than left to be discovered mid-E2.
- The existing file-based `RunStore` persistence pattern (C1) is the template for agent-run persistence, not something to be replaced by a new database — `engine.py`'s `run_pipeline()` itself is not reused directly (its fixed 8-`StageName` linear-pipeline shape doesn't fit a dynamic tool-calling agent loop), but the *pattern* (hash-based reuse-vs-rerun, file-based `RunRecord`/`StageRecord`-shaped persistence) carries over into a new, sibling `ai/orchestration/` module.
- `src/features/investigation/workspace/panel/AskTab.tsx` stays exactly as its D0.3 disclosed placeholder until E6 — this ADR does not authorize touching it before E6 is separately approved.

## Alternatives Considered

- **Use a paid hosted API (e.g. Anthropic) as the real provider.** Rejected for now: directly requires an `AGENTS.md` §5 cost exception, and while it would very likely produce more reliable structured output/tool-use behavior (a real, acknowledged tradeoff — see Decision §2), Kamal chose to stay inside the existing free-infrastructure constraint rather than request the exception. This can be revisited explicitly later if Ollama's output quality turns out to undermine the E7 evaluation's ability to say anything meaningful.
- **Defer picking a real provider until E1's Planner/Analyst are ready to test against it.** Considered as a third option when this was asked; rejected in favor of deciding now, since it lets E1's `OllamaProvider` implementation be written directly rather than through an interim placeholder.
- **Keep the old Phase E-L roadmap content and layer the new AI-core sequence alongside it as a "superseded" appendix**, rather than replacing it. Rejected: leaves two roadmaps to reconcile mentally, the same problem ADR-002 already rejected once for the D0 insertion; a clean replacement with the old content's absorption into F/G explicitly noted (Decision §3) is more legible going forward.
- **Treat this as an insertion ahead of the existing Phase E** (an "E0" sub-phase, mirroring how Phase D0 was first proposed before ADR-002 chose full insertion instead). Rejected: the new instruction set's own Phase E is explicitly the AI core, not a preface to source discovery — a sub-phase framing would misrepresent that AI Core is now the roadmap's primary spine, not a detour before it.
